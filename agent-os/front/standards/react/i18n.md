# i18n — no hardcoded user-facing strings

Every string a user can read renders through `t(...)` (react-i18next). A literal display
string in a component is a bug, even in English: placeholders, labels, button text,
tooltips, empty states, `aria-label`s, option labels, toasts and error messages.

```tsx
// WRONG — hardcoded, and French on top
<DelayedFieldSearchbar placeholder="Rechercher" />

// RIGHT
const { t } = useTranslation();
<DelayedFieldSearchbar placeholder={t("pages.advancedFolderSearch.searchPlaceholder")} />
```

- Keys live in every locale bundle of `src/utils/translate/*.json` (`fr`, `en`, `es` today —
  list the folder, do not trust this sentence), mirrored: every key exists in every file, with
  a real translation, added in the same commit. Error notices follow the same rule in
  `src/utils/translate/errors/*.json`.
- `src/__tests__/utils/translate/esTranslations.test.ts` enforces key parity across bundles. It
  is a targeted gate for any change touching a locale file: run it, and never classify its red
  as pre-existing when your diff adds keys.
- Reuse an existing key before adding one; key paths mirror the feature
  (`pages.<feature>.<thing>`).
- Table headers (`header: t("...")`) and zod error messages are i18n keys too — see
  `react/data-tables` and `react/forms`.

## Verbatim exceptions — keep literal, do NOT wrap in t()

Same boundary as `naming-language`: a string that must equal something a backend or a
browser already knows is data, not copy.

| Kind | Example |
|------|---------|
| Backend contract value | `viewModel: "GestionMotifsFavorisViewModel"` |
| Route URL segment | `path: "motifs-favoris"` |
| API-returned business label | a `name`/`label` value the API emits (render as-is) |

Rule of thumb: if you authored the string for a human to read, it is a `t(...)` key. If it
must match an external contract, it stays verbatim.
